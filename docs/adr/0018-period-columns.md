# ADR 0018: Period columns are ordered by the server, with PeriodO as the reference

Date: 2026-11-14. Status: accepted.

Archaeological data puts time in a text column: "Hellenistic", "Geç Tunç Çağı", "EB II", "Glockenbecherkultur", "MÖ 5. yüzyıl", "1500 BC". Text sorts alphabetically, so a chart drew Byzantine before Chalcolithic. Such a column now gets the profile type `period`, and every chart that encodes it is drawn oldest first.

**Where the dates come from.** Period names are dated from [PeriodO](https://perio.do), the gazetteer of period definitions published by named sources, vendored as a snapshot (`datasets/periodo_snapshot.json`, CC0, rebuilt with `manage.py periodo_snapshot`). A first version used a table of period names and round dates written by us; it was rejected the same day. It knew one region, failed on German names and on anything outside the eastern Mediterranean, and put our own dates where published ones exist. With PeriodO each placed value carries the id and source of the definition that placed it, which the dataset page shows and the export bundle keeps. The snapshot is vendored rather than queried because calling perio.do would send users' cell values to a third party, and because a chart must reproduce after PeriodO changes.

**What PeriodO does not do, and what fills the gap.**
- It does not read dates. "1500 BC", "MÖ 5. yüzyıl", "9000 BP" are parsed directly.
- It has many definitions of one name: "Iron Age" has 86, starting between 1600 and 400 BC. The column is read as a whole: the region most labels have a definition for wins, and within it the definition nearest the middle of the candidates, so one eccentric source does not decide.
- It has almost no Turkish period names (its Turkish labels are Ottoman reigns) and few German ones, and it is literal about wording. A glossary of words, not dates, translates Turkish and German labels into the English most sources use, and common abbreviations are expanded. The date still comes from PeriodO.
- It does not know site phases, and no list will.

**What is left is for the user and, if they ask, their model.** The first real dataset tried, an Aegean zooarchaeology table, had 54 distinct period values of which fewer than half could be read: `LN`, `FN`, `ECh`, `LH IIIB-C`, `Palatial`, `C-PPNA`. Shorthand like that is the normal case, so the dataset page lists every value with what placed it and a field to say what it means, as a period name or a date. A meaning is read like any other label, so it is dated by PeriodO when it is a name, and it overrules what was found. The page also lets the user type the whole order, and offers to ask the user's model about the values still unplaced. That request sends one column's distinct values to the user's endpoint, so it happens only on an explicit click, per column, and its messages and raw answer are stored with the dataset. The model is asked for a period name, which is looked up in PeriodO like any other label; its own years are used only when PeriodO has no such name, and are shown as an estimate.

**A dataset that carries its own dates can say so.** Many tables define their periods themselves, in a start year and an end year column beside the label. Which columns those are is not detected: on the test table the two date columns could not be told from a longitude column by their values, and rules written from a few files would not hold for the next one. The user declares it instead, with one link per period column (start column, optional end column, whether years are counted BC). Each value is then placed by the earliest start and the latest end among its rows, ahead of PeriodO, and values whose rows carry no dates are still looked up. One label often has different dates at different sites, so the widest span is used and the value is marked as varying. A meaning the user typed for a value still comes first.

**Why the server sorts, not the chart model.** The chart model sees at most five values of a column and none at the `minimal` privacy level; its order would differ between runs and providers, and a wrong order is an error a reader of the chart does not notice. The validator writes the order into the stored spec as an explicit `sort` list. The chart prompt changed only to say that a `period` field is ordinal and is sorted after the answer (`p2026-11-a`); revisions made with `p2026-09-a` keep their record and replay as before.

**Known limits.** Detection is strict (bare "Iron" is a material, PeriodO's entries for sultans or for the word "Early" do not make a period column) because a false `period` reorders a chart silently, while a missed one is one click to correct. Mixing sources within a column can put a sub-period slightly out of step with its parent. The region is inferred, not chosen: there is no control for it yet, only the meanings and the typed order.
